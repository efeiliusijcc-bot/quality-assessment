1. 设计目标与建设边界

1.1 设计目标

本设计文档面向“视觉检测融合知识图谱与深度学习的电子元器件装配生产质量评估”项目，给出 Neo4j 图数据库的节点、关系、属性、约束、导入与查询设计。Neo4j 不替代 PostgreSQL 的业务数据存储，而是作为质量评估知识图谱的关系表达、影响链路分析和可视化查询平台。

将工序、设备、工位、工艺参数、质量指标、缺陷类型、生产批次、检测任务、评估结果等对象表达为图节点。

将工序先后关系、参数归属关系、参数影响质量指标、参数诱发缺陷、缺陷属于工序、批次经过工序等表达为图关系。

将规则引擎、Apriori 关联挖掘和图注意力网络 GAT 输出的影响权重落到关系属性中，实现可解释的质量因素分析。

支撑软件平台中的质量合格性评估、研判性评估、预测性评估、缺陷溯源、参数推荐和图谱可视化。

1.2 建设边界

PostgreSQL 负责保存完整的业务明细数据，例如工序执行记录、参数采集值、质量检测值、缺陷检测记录、评估任务、优化结果等；Neo4j 重点保存“对象之间的关系网络”和“关系权重”。因此，Neo4j 不建议保存所有原始时序数据、图片文件、视频流和大规模日志，只保存它们的索引、摘要或业务引用 ID。

2. 总体架构设计

整体架构建议采用“PostgreSQL 业务数据层 + ETL/规则处理层 + Neo4j 知识图谱层 + GAT 图学习层 + 软件平台应用层”的五层结构。

多源数据采集

  ├─ 设备接口 / RESTful API

  ├─ Excel 批量导入

  ├─ AOI / 视觉检测系统

  ├─ 人工录入

  └─ 仿真与优化算法输出

        ↓

  ├─ core：工序、设备、参数、产品等基础字典

  ├─ qc：质量指标、检测任务、缺陷记录

  ├─ eval：质量评估、预测、优化结果

  └─ kg：图谱实体、关系、GAT 权重中间表

        ↓

  ├─ 节点：工序、参数、缺陷、指标、设备、批次、评估结果

  └─ 权重：rule_weight、apriori_confidence、gat_weight

        ↓

业务应用

3.1 推荐的 PostgreSQL 中间视图

为了避免业务表直接和 Neo4j 导入脚本强耦合，建议在 PostgreSQL 中维护两个导出视图：kg.v_neo4j_node_export 和 kg.v_neo4j_relation_export。视图负责将业务表中的对象统一转成 node_id、node_label、properties 和 relation_type、source_node_id、target_node_id、weight 等通用字段。

-- 节点导出视图示例

CREATE OR REPLACE VIEW kg.v_neo4j_node_export AS

SELECT

    entity_id::text AS node_id,

    entity_type AS node_label,

    entity_code,

    entity_name,

    ref_schema,

    ref_table,

    ref_id::text AS ref_id,

    properties

FROM kg.kg_entity;

-- 关系导出视图示例

CREATE OR REPLACE VIEW kg.v_neo4j_relation_export AS

SELECT

    relation_id::text AS relation_id,

    source_entity_id::text AS source_node_id,

    target_entity_id::text AS target_node_id,

    relation_type,

    relation_weight,

    confidence,

    evidence_source,

    evidence_payload

FROM kg.kg_relation;

6.3 权重解释建议

为了便于解释，建议把关系权重分为三类：规则权重、统计权重和模型权重。最终展示时可使用综合权重 final_weight，也可以分别展示 evidence_source 和 gat_weight。

final_weight = 0.4 * rule_weight + 0.3 * apriori_confidence + 0.3 * gat_weight

说明：

- rule_weight：来自专家规则或规则引擎，强调确定性知识；

- apriori_confidence：来自频繁共现关系，强调统计相关性；

- gat_weight：来自图注意力网络，强调模型学习到的潜在影响强度。

8. PostgreSQL 到 Neo4j 的导入方案

推荐两种导入方式：第一种是后端服务直接从 PostgreSQL 查询并调用 Neo4j Driver 写入；第二种是由 PostgreSQL 导出 CSV，再使用 Neo4j LOAD CSV 导入。开发阶段可用 CSV，正式系统建议使用后端同步服务，便于做增量、重试和日志记录。

8.1 全量初始化流程

步骤 1：清空或新建 Neo4j 数据库，并创建约束和索引。

步骤 2：从 PostgreSQL 导出静态字典：工序、参数、质量指标、缺陷类型、设备、工位、产品型号。

步骤 3：导入静态节点和静态关系，例如 NEXT、HAS_PARAMETER、HAS_DEFECT、HAS_QUALITY_METRIC。

步骤 4：导入已有生产实例数据，例如批次、工序执行、检测任务、缺陷记录和评估结果。

步骤 5：导入规则、Apriori 和 GAT 产生的 AFFECTS、CAUSES、CO_OCCURS_WITH 等关系权重。

8.2 工序节点导入示例

MERGE (s:ProcessStep {step_id: $step_id})

SET

    s.step_code = $step_code,

    s.step_name = $step_name,

    s.step_order = $step_order,

    s.is_inspection = $is_inspection,

    s.source_system = 'PostgreSQL',

    s.updated_at = datetime();

8.3 参数节点导入示例

MERGE (p:Parameter {param_id: $param_id})

SET

    p.param_code = $param_code,

    p.param_name = $param_name,

    p.param_category = $param_category,

    p.data_type = $data_type,

    p.unit = $unit,

    p.lower_limit = $lower_limit,

    p.upper_limit = $upper_limit,

    p.source_system = 'PostgreSQL',

    p.updated_at = datetime();

8.4 工序包含参数关系导入示例

MATCH (s:ProcessStep {step_id: $step_id})

MATCH (p:Parameter {param_id: $param_id})

MERGE (s)-[r:HAS_PARAMETER]-&gt;(p)

SET

    r.source = 'PG_DICT',

    r.updated_at = datetime();

    r.relation_id = $relation_id,

    r.weight = $relation_weight,

    r.confidence = $confidence,

    r.evidence_source = $evidence_source,

    r.evidence_payload = $evidence_payload,

    r.updated_at = datetime();

10. 典型查询与业务应用

10.1 查询某缺陷可能由哪些参数导致

MATCH (p:Parameter)-[r:CAUSES]-&gt;(d:DefectType)

WHERE d.defect_name CONTAINS $defect_name

RETURN

    p.param_name AS 参数,

    p.param_category AS 参数类别,

    r.weight AS 综合权重,

    r.gat_weight AS GAT权重,

    r.confidence AS 可信度,

    r.evidence_source AS 证据来源

ORDER BY coalesce(r.gat_weight, r.weight, r.confidence) DESC

LIMIT 20;

10.2 查询影响某质量指标的关键工艺参数

MATCH (p:Parameter)-[r:AFFECTS]-&gt;(m:QualityMetric)

WHERE m.metric_name CONTAINS $metric_name

RETURN

    p.param_name AS 参数,

    p.unit AS 单位,

    r.weight AS 综合权重,

    r.gat_weight AS GAT权重,

    r.evidence_source AS 来源

ORDER BY coalesce(r.gat_weight, r.weight) DESC

LIMIT 20;

10.3 查询某工序的完整质量知识子图

MATCH (s:ProcessStep {step_name: $step_name})

OPTIONAL MATCH (s)-[:HAS_PARAMETER]-&gt;(p:Parameter)

OPTIONAL MATCH (s)-[:HAS_QUALITY_METRIC]-&gt;(m:QualityMetric)

OPTIONAL MATCH (s)-[:HAS_DEFECT]-&gt;(d:DefectType)

RETURN s, collect(DISTINCT p) AS 参数, collect(DISTINCT m) AS 质量指标, collect(DISTINCT d) AS 缺陷类型;

10.4 查询某批次的生产与缺陷追溯链

MATCH (b:Batch {batch_no: $batch_no})-[:HAS_RUN]-&gt;(run:ProcessRun)-[:EXECUTES_STEP]-&gt;(s:ProcessStep)

OPTIONAL MATCH (run)-[:HAS_INSPECTION]-&gt;(it:InspectionTask)-[dr:DETECTED_DEFECT]-&gt;(d:DefectType)

RETURN

    b.batch_no AS 批次号,

    run.run_no AS 工序执行号,

    s.step_name AS 工序,

    d.defect_name AS 缺陷,

    dr.defect_count AS 缺陷数量,

    dr.confidence AS 置信度

ORDER BY s.step_order;

10.5 查询质量风险最高的批次

MATCH (b:Batch)-[:HAS_ASSESSMENT]-&gt;(ar:AssessmentResult)

RETURN

    b.batch_no AS 批次号,

    ar.assessment_score AS 质量评分,

    ar.pass_probability AS 合格概率,

    ar.risk_level AS 风险等级,

    ar.conclusion AS 结论

ORDER BY ar.pass_probability ASC, ar.assessment_score ASC

LIMIT 20;

10.6 查询优化算法推荐的参数调整方案

MATCH (or:OptimizationResult)-[r:RECOMMENDS]-&gt;(p:Parameter)

WHERE or.result_id = $optimization_result_id

RETURN

    p.param_name AS 参数,

    p.unit AS 单位,

    r.original_value AS 原始值,

    r.recommended_value AS 推荐值,

    r.delta AS 调整幅度,

    or.algorithm_name AS 算法,

    or.pareto_rank AS Pareto排名

ORDER BY or.pareto_rank, abs(r.delta) DESC;

11. 数据更新策略与运行维护建议

11.1 更新策略

数据类型

更新频率

同步策略

工序、参数、质量指标、缺陷类型等字典数据

低频

手动触发或每日全量校验同步

批次、工序执行、检测任务、缺陷记录

高频

按批次或按时间戳增量同步

质量评估结果、预测结果、优化结果

中频

评估任务完成后实时写入 Neo4j

规则关系、Apriori 关系

中低频

规则更新或数据挖掘任务完成后批量更新

GAT 权重

按模型训练/推理批次

11.2 增量同步字段建议

PostgreSQL 中每张需要同步到 Neo4j 的表建议保留 created_at、updated_at、deleted_flag 或 sync_status 字段。同步程序记录 last_sync_time，每次只抽取 updated_at 大于 last_sync_time 的数据。

-- 增量同步基本逻辑

SELECT *

FROM kg.v_neo4j_node_export

WHERE updated_at &gt; :last_sync_time;

SELECT *

FROM kg.v_neo4j_relation_export

WHERE updated_at &gt; :last_sync_time;

11.3 运行维护建议

保持 PostgreSQL 为业务数据主库，Neo4j 中的数据可以重建，不应成为唯一主数据源。

所有 Neo4j 节点和关系都应保留来源表和来源 ID，保证可追溯。

GAT 权重需要记录模型版本，否则不同版本模型输出的权重无法对比。

高频生产数据不要无限制写入 Neo4j，建议按批次、按工序执行摘要导入，原始曲线仍保存在 PostgreSQL 或文件存储。

前端可视化图谱应限制返回节点数量，避免一次性展示全图造成性能问题。
